# Sony SPC700 (SNES audio CPU)

Ghidra processor module for the Sony SPC700, the S-SMP sound CPU of the Super Nintendo. It has
two language variants with identical p-code that differ only in mnemonics:

| Language ID | Syntax | Example |
|---|---|---|
| `spc700:LE:16:default` | Sony (SNES development manual) | `MOV A,[0x12]+Y`, `OR1 C,/0x1412.0x1` |
| `spc700:LE:16:65816` | 65816-style, as in bass's `spc700.arch` table (shipped in `data/languages`) | `LDA (0x12),Y`, `ORC !0x1412:0x1` |

It also has a loader for `.spc` snapshots (`SPC700`; 64 KB RAM, the S-DSP registers as the
overlay block `DSP`, entry point from the saved PC or the "Entrypoint Address" option).

This is a community module: qwertymodo's [SPCdra](https://github.com/qwertymodo/SPCdra)
(Apache-2.0). Ghidra-Rare regenerated its SLEIGH from one table to fix decoding and the p-code.
See [CREDITS.md](CREDITS.md) for every change (a fork commit per change).

## What it covers

- All 256 opcodes. Both `.slaspec` files are generated by `tools/gen_spc700.py`; edit the
  generator, not the specs.
- Direct page follows PSW.P: `SETP`/`CLRP` set a decode context, so direct-page operands get
  constant addresses `$00xx`/`$01xx`; `POP PSW` restores the P saved by a `PUSH PSW` on the same
  flow path. The SPC loader takes the initial P from the saved PSW.
- The flags are separate registers (`CF ZF IF HF BF PF VF NF`); `YA` is the A/Y pair.
- The stack is in page 1. `CALL`/`PCALL`/`TCALL`/`BRK` push the return address, `RET`/`RETI` pull
  it, and `TCALL n`/`BRK` call through the vectors at `$FFDE-2n`/`$FFDE`.
- `$F0-$FF` (I/O registers) are volatile, and the loader labels them. The 128 S-DSP registers
  (reached only through the `$F2`/`$F3` window) are loaded from the `.spc` file into the overlay
  block `DSP` with their names (`V0VOLL` ... `KON`, `FLG`, `DIR`, `ESA`, `EDL`, `FIR0-7`).
- `SLEEP` and `STOP` halt: a self-loop with no fall-through (the SNES gives the SPC700 no
  interrupt to wake it), so emulation stays on them.

## How to test

```sh
export GHIDRA_INSTALL_DIR=/opt/ghidra_12.1.4_PUBLIC
BASS=/path/to/bass SINGLESTEP=1 REAL_SAMPLES=/path/to/samples test/run-tests.sh /path/to/workdir
```

`BASS` (built from [ARM9/bass](https://github.com/ARM9/bass), with its `architectures` folder next
to the binary) enables the 65816-style round trip and rebuilds the emulator test program.
`SINGLESTEP=1` fetches SingleStepTests/spc700 (about 80 MB). `REAL_SAMPLES` fetches the driver
and ROMs by pinned URL and SHA-256 (`test/fetch-real-samples.sh`). If `mame` is installed, it
traces and dumps them, using an independent SPC700 boot ROM (`test/trace/make_ipl.py`) so Sony's
IPL is never needed. Nothing fetched is committed.

## Known gaps

Fixed in the limitations pass (each with a test that fails before the change):

- P context after `POP PSW`: restored from a `PUSH PSW` on the same flow path (`4d14cac`).
  `RETI` has no fall-through, so the P it pulls never decides a decode.
- `SLEEP`/`STOP`: self-loops instead of pcodeops (`e308242`); SingleStepTests 2,000/2,000.
- `TCALL`/`BRK` at `$FFFF` push return address `$0000` (`e2c00b6`).
- The 128 DSP register bytes of a `.spc` file are loaded (`DSP` overlay block, `cae8ae7`).

Remaining, and why:

- Instructions whose own bytes run past `$FFFF` (5 SingleStepTests cases: a 2- or 3-byte
  instruction at `$FFFE`/`$FFFF`) are not decoded: Ghidra requires an instruction to lie inside
  its address space, which a SLEIGH spec cannot change. Real code never sits there (`$FFC0-$FFFF`
  is the boot ROM).
- DSP and timer *behaviour* is not modelled: they are peripherals behind `$F2`/`$F3` and
  `$FA-$FF`, which Ghidra's emulator has no model for (hardware state outside the CPU). The
  register values are loaded and named.
- The boot ROM (IPL) overlay at `$FFC0`: its 64 bytes are Sony's copyrighted code and are not
  shipped; the address is labelled `IPL`.
- Jump tables bounded only by protocol (SNESMOD's `AND #$7F; ASL; JMP [!abs+X]` with 12 valid
  entries) make Ghidra's switch recovery read 128 entries and time out, so the command handlers
  are found only from other references. This is the decompiler's jump-table recovery, outside the
  module; the bound is not in the code.
- Finding the driver entry point (upstream README, bsnes+ procedure): a `.spc` file does not
  record where the boot ROM started the driver. The boot ROM leaves the address in `$0000-$0001`,
  but SNESMOD clears page 0 first thing: the word there is `$613C`, `$5A3E` and `$FF92` in the
  three MAME dumps, never the entry `$0400`. A scan for a stack set-up (`MOV X,#imm; MOV SP,X`)
  finds nothing in SNESMOD (it never sets SP), and the saved PC is in the main loop. None of
  these is reliable, so the loader does not guess; it starts from the saved PC (or the option).

## Reference-tool bugs found

- MAME's spc700 disassembler decodes `NOT1 m.b` (`$EA`) as a 1-byte instruction. Its own CPU core
  (`OP_NOT1`) reads a 16-bit operand, so Ghidra's 3-byte decode is checked against the encoding.
- MAME omits the implied `YA` of `CMPW`/`ADDW`/`SUBW`.
- bass rejects some `$h:` forms (`set $0:0`); the round trip writes decimal numbers instead.
